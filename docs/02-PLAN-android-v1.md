# План: Android-приложение «Тренировочная система» — v1

Опирается на `00-REVERSE-oge-trainer-web-v1.md` (что переносим) и `01-TZ-android-v1.md` (что требуется). Сроки считаны при 32 рабочих часах в неделю и буфере 15 %.

## 1. Главный вывод

Перенос «полного функционала» — это не перенос контента: контент генерируется LLM на сервере (в базе 31 задача и 47 конспектов против 103 тем). Переносится клиент: 8 экранов, 23 REST-метода, 5 предметов, 4 режима ответа, 3 роли. Полная офлайн-работа без сервера невозможна; офлайн — только чтение и очередь ответов.

Отсюда объём: **120 ч до работающего MVP** (ученик + родитель на телефоне, сервер с защитными доработками), **201 ч до полной версии** с админкой, офлайном и релизной подготовкой.

## 2. Принципы

1. Вертикальные срезы: каждая фаза заканчивается сквозным сценарием на устройстве, а не «слоем».
2. Первый гейт — самый рискованный: рендеринг формул (KaTeX) проверяется в первые три дня, до вёрстки остальных экранов.
3. Проверка на двух контурах: AVD API 36 (быстро, для UI-тестов) и физический телефон (честные замеры старта и прокрутки).
4. Серверные доработки — отдельной волной в начале, чтобы клиент не кодировал обходы (refresh, идемпотентность, лимиты).
5. Ни одна цифра прогресса не считается в клиенте: показывается то, что вернул сервер.

## 5. Порядок работ для ИИ-исполнителя

Каждый шаг заканчивается проверкой; без зелёной проверки следующий не начинается.

1. Прочитать `AGENTS.md`; сверить версии с кэшем Gradle (`~/.gradle/caches`), не тянуть «последние» из сети.
2. Создать проект, `assembleDebug` на AVD — проверить: APK собирается, приложение запускается.
3. Внести токены темы и компоненты — проверить: экран-заглушка выглядит как веб (цвета, радиусы, плотность).
4. Реализовать `ApiClient` + `TokenStore` + вход — проверить: вход `ivan`, выход, сохранение токена после перезапуска.
5. Проверить 401 (стереть токен) — приложение возвращается на вход без падения.
6. Спайк рендера формул (P1-1) — зафиксировать решение в `AGENTS.md` до начала вёрстки задач.
7. Экран предметов и дерево тем — проверить: mastery приходит и отображается, пустой список обработан.
8. Экран теории — проверить: первый заход генерирует конспект, второй берёт из кэша, 502 показывает «Повторить».
9. Экран задачи — проверить: 4 режима, короткий ответ точным совпадением принимается без LLM.
10. Экран результата — проверить: `points/max_points` для развёрнутого, ok/partial/bad цвета.
11. Outbox — проверить: ответ при выключенной сети уходит после включения; в `attempts` одна запись.
12. Отчёт и очередь проверки — сверить цифры с `curl` ответом API на том же пользователе.
13. Админка — пройти 4 операции, каждую подтвердить перечитыванием списка.
14. Release-сборка — проверить: `assembleRelease` с keystore, установка на устройство, `adb backup` без токена.
15. Прогон AC-1…AC-10, заполнить таблицу результатов в `docs/03-AC-results.md`.

| ID | Риск | Вероятность / влияние | Мера |

## 8. Что требуется от заказчика

1. **Устройство и версия Android** для эксплуатации (от этого зависит `minSdk` и объём тестов) — OQ-1.
2. **Решение по админке**: переносить целиком или оставить в вебе (форма AI-провайдера — кандидат на исключение) — OQ-2.
3. **Разрешение на серверные правки** FR-S1…S8 на `170.168.100.53`: без S3 (лимиты), S4 (идемпотентность), S6 (секрет и пароли), S8 (бэкап) бета-сборку выпускать нельзя. Правки трогают `oge-api`, `.env` и compose — нужен отдельный слот времени и подтверждение на рестарт стека.
4. **Бюджет DeepSeek**: замер — 180 токенов на генерацию, 142 на проверку; при 20 заданиях в день это единицы копеек, но квота (S3) ставится по вашему решению.
5. **Канал распространения**: APK по ссылке или RuStore (OQ-4); при RuStore — аккаунт разработчика и скриншоты.
6. **Пароль от keystore** для release-сборки (хранится у вас, не в репозитории).
